## 1. Wire rules

- **Ids**: opaque strings `^[A-Za-z0-9_-]{1,64}$`. `tripId` is the trip. `offerId` is an offer (one trip, many offers). `rideId` is a read-only legacy alias of `tripId`. Clients never invent a `tripId`.
- **Time**: RFC 3339 UTC with `Z`. Durations are integer seconds. Zone-local wall times (surge windows, `HH:mm`) carry the zone `timeZone`.
- **Money**: `{ "amountMinor": int, "currency": "SEK" }`. Exponent from ISO 4217 (`SEK`/`EUR` 2, `TND` 3). No floats, no display strings (`"126,75 kr"`) on the wire. Apps format locally.
- **Location**: `Place { address?, lat, lng }` for pickup, dropoff, stops (ordered). `GeoFix { lat, lng, accuracy, heading?, speedMps?, moving?, measuredAt }` for device GPS only; `moving` is the driver app's stopped / driving judgement (§3.3). JSON says `lat`/`lng`; Dart may keep `latitude`/`longitude` inside.
- **Location exception (v0.5.1)**: the bodies of `POST /locations/autocomplete`, `/locations/geocode` and `/locations/reverse-geocode` say `latitude`/`longitude`, the names the rider app sends and reads (§10). This is the only exception; `POST /routes` and everything else keep `lat`/`lng`.
- **Case**: keys camelCase, enum values snake_case.
- **Categories**: ids from the admin Pricing catalog (`^[a-z][a-z0-9_]{1,31}$`). Seed: `economy, comfort, premium, priority, xl, electric, pet, child_seat` (v0.6.0), labels Movera, Comfort, Premium, Priority, Movera XL, Electric, Movera Pet, Child Seat (`contract.json#categories.labels`). Aliases `movera → economy` and (v0.6.0) `kids → child_seat` accepted on read for one release. Labels are display only; the admin catalog adds, deletes and deactivates categories and the apps follow it.
- **Payment methods**: `card, apple_pay, cash, wallet` (a saved card is `card` + `paymentMethodId`). Every country offers at most these three (`contract.json#zonePaymentMethods`: `cash, card, apple_pay`, owner Q7; v0.18.10 owner G8: Google Pay removed, cash shown as "Pay in car"; the admin turns each on per country / zone and the server says which it takes, §36). No `swish`, no `d17`. `wallet` is never a config payment method: it is one balance per currency (no conversion), used first. The v0.3 id `apple` is accepted on read as `apple_pay` for one release.
- **Languages**: `en, fr, sv` (`contract.json#languages`). Admin sets the default per country for the rider, driver and admin apps; the user can change it.
- **Headers**: `Idempotency-Key` on every mutation (16–128 chars, server 409s on a different body under the same key), `X-Request-Id`, `X-Api-Version: 0.5`.
- **Read-only POSTs (v0.5.1)**: `POST /locations/*`, `POST /routes`, `POST /admin/auth/setup-password/check` and `POST /telemetry/*` change nothing (`x-read-only` in `openapi.yaml`): they take no `Idempotency-Key` and the server must not ask for one. Telemetry also needs no bearer token and no standard headers (§11).
- **Concurrency**: every trip/offer/driver/config command sends `expectedVersion`; a stale version gets `409 version_mismatch` with the current projection. The one exception is the rider's after-cancel reason (`POST /trips/{tripId}/cancel-reason`, §3), which does not change the trip's version.
- **Errors**: `{ code, message, requestId, retryable, reason?, projection?, details? }` (`details`, v0.14.0: an optional list, e.g. the document types of `documents_not_approved`), codes in `contract.json#errors.codes`; `reason` is an optional machine-readable detail under the code (`invalid_phone`, `invalid_otp_code`, …), never shown as is. `projection` is the current resource for `version_mismatch` / `invalid_transition` (trip, offer, driver, rider, vehicle or config draft). Validation and wrong PIN are 400 `invalid_request`; too many PIN attempts 429. Success responses are the bare resource.

Status enums (exact values in `contract.json`): `TripStatus` (19), `PaymentStatus`, `RatingStatus`, `DriverAccountStatus`, `DriverOnlineStatus`, `OfferKind`, `OfferStatus`.

**Payment and rating are not trip statuses.** After `completed` they change as fields on the projection (`payment_updated`, `rating_updated` events) and are never blocked by the terminal rule. Rider UI states like `paymentProcessing`, `ratingPending`, `paymentFailed` are derived: `completed + paymentStatus`, `completed + ratingStatus`.

**Who may rate** (`contract.json#ratingAllowed`): the rider and the driver after `completed`; the rider also after a trip the rider ended early (`end_early` → `cancelled_by_rider`, `POST /trips/{id}/end-early`), with the normal rating screen. `ratingStatus` then goes `pending → submitted | skipped` and `rating_updated` passes the terminal gate as usual. A plain rider `cancel` (also `cancelled_by_rider`) is never rated; the driver rates an ended-early trip too (v0.18.50 §72 L5, owner G8 Q1: the driver gets the normal finish); any other rating is `409 invalid_transition`. The marker is the command that ended the trip: `end_early` is only allowed on board and `cancel` by the rider only before boarding, so the server knows which one ended it.

## 3. Trip lifecycle (single state machine)

The transition table is `contract.json#transitions`: `command × actor × from[] → to`, with `when: live | scheduled` where the target differs. Anything not in the table is `409 invalid_transition` and the status does not change.

```
draft → quoted → requested → searching ⇄ offered → accepted → driver_to_pickup → arrived → rider_onboard → in_trip → approaching_dropoff → completed
                         (scheduled: requested ──driver claims──▶ accepted)
Terminal: completed · cancelled_by_rider · cancelled_by_driver · cancelled_by_admin · cancelled_by_system · no_show · expired · failed
```

| Command (actor) | From | To | Rider app | Driver app | Admin |
|---|---|---|---|---|---|
| quote (system) | draft | quoted | Price per category | — | Quote kept on the trip |
| request (rider) | quoted | requested | "Finding driver" / booked reservation | — | Trip appears in lists |
| start_search (system) | requested | searching | Searching animation | — | Live map: searching |
| send_offer (system) / assign (admin) | searching (admin: requested, searching, offered) | offered | Still searching | Radar / Exclusive / "Assigned by Movera" card (Priority badge when `priority`) | Direct assign or radar group (§3.1); sees offers and countdown |
| offer_lapsed (system) | offered | searching | — | Card gone ("taken" / expired) | — |
| accept (driver) | offered (scheduled: requested) | accepted | Driver card, car, ETA | Trip screen / Accepted reservation | Driver shown on trip; assignment locked |

### 3.1 Admin dispatch tooling (owner Q13–Q18)

Both tools are the admin `assign` transition (`contract.json#adminDispatch`); the trip stays `offered` until one driver accepts.

- **Direct assign** `POST /admin/trips/{id}/assign {driverId}`: an exclusive offer (`kind = assigned`, `source = admin`) to one driver, who accepts or declines within `offers.exclusiveSeconds`. It counts as an exclusive offer (acceptance rate, auto-offline; v0.18.6 owner G4-E3 "Count them": a declined or missed one counts toward the in-a-row limit).
- **Radar group** `POST /admin/trips/{id}/radar-group {driverIds[1..10]}`: one `radar` offer per chosen driver with the same `groupId`, on the zone's normal timer (`offers.radarSeconds`); the admin sees the countdown (`expiresAt`). The first to accept wins, the others get `offer_withdrawn` (`claimed_elsewhere`). Groups can be repeated while the trip is not locked.
- **Nearby drivers** `GET /admin/trips/{id}/nearby-drivers?scope=radius|zone|zone_and_neighbours&radiusKm=` (presets 5 / 7 / 10 km or any number).
- **Lock**: once a driver accepts (`status` in `driverAssigned` or terminal), `assign` and `radar-group` are `409 invalid_transition`.
- **Driver bonus** ("add money to trip"): `driverBonus: Money` on assign / radar-group, or `POST /admin/trips/{id}/driver-bonus`. Paid by Movera (from its commission, possibly beyond it); the rider never pays it. The driver's `Offer.fare` and `driverEarnings` already include it, and `priority: true` shows the "Priority" badge. Above the country's `driverBonus.defaultLimit` the server answers `400 invalid_request` ("adjust the limit in Pricing"); the limit can never exceed `driverBonus.hardMax`. **Apply to** (owner bug 2026-11-01): optional `applyTo: exclusive | radar | both` on driver-bonus, assign and radar-group — the money and the Priority badge go only to offers of that kind (exclusive = `assigned` + automatic `exclusive`); default both on driver-bonus, the send's own kind on assign / radar-group; with applyTo the server also sends at once (owner decision 2026-11-01): Exclusive → exclusive offer to the nearest free driver when none is out; Radar → open exclusive offers become radar + radar to the nearest free drivers when none is out; Both → exclusive to the nearest and radar to the others; the answer adds `moneySend { exclusiveTo, radarTo, skipped { expired, busy, far }, reachKm }` (skipped/reachKm: live fix 2026-11-02, additive; counts are drivers, each once: expired and far = the larger of the kinds looked at, busy = the sum over the sends, which go to different drivers); nobody free → the money waits; v0.18.11: "nearest free" follows the zone's dispatch settings — in-zone first, neighbours (same country) only when none free, never beyond the widest step of that mode (`exclusive.steps` / `radar.steps`, else `radius.steps`) nor `limits.maxPickupKm` / `maxPickupEtaMin` (km ÷ 24 km/h); the limit counts per kind; accept keeps the money of the kind taken. Admin view: `driverBonusByKind { exclusive, radar }` (contract.json#adminDispatch.driverBonus.applyTo).
- **Events**: `GET /admin/dispatch/stream` (SSE, `AdminDispatchEvent`): `offer_sent, offer_declined, offer_expired, offer_withdrawn, offer_accepted, assignment_locked, driver_bonus_added`. The rider only sees "searching" then "driver assigned".
- **One admin is enough (v0.7.2, owner 2026-10-28; replaces the second-admin rule of v0.5.1)**: every admin with the permission runs refunds, adjusts, config publishes, surge and dispatch control at once (`200`/`201`) and it is written in the audit; no operation answers `202 pending_approval`. Before v0.7.2: **Second-admin approval (v0.5.1, owner decision 14 (2026-10-24))**: a Super admin (role `super`, `AdminMe.approvalExempt: true`) never needs a second admin: refunds, adjusts, config publishes, surge and dispatch control run at once (`200`/`201`, never `202 pending_approval`) and are written in the audit. Big changes by other admins still answer `202 pending_approval` and wait for another admin (`POST /admin/approvals/{id}/approve`, `approval.decide`; for dispatch rules the panel's `dispatch.approve`).

### 3.2 Pickup pay (v0.5.0, owner decision 7)

Two separate sides (`contract.json#pickupPay`, Admin Pricing › Pickup pay, per zone and category). Cases every app's maths must reproduce: `fixtures/pickup_pay.json`.

- **Rider side, a fixed fee.** `PickupPayRate.riderFee { live: Money | null, reservation: Money | null }`: one amount for live rides (Radar and Exclusive), one for reservations, `null` = off. When on, the quote carries it as the `pickup_fee` fare line and the rider pays it whatever driver comes or how far away they are; Movera keeps it. The rider document names the fees in `pickupFee.byCategory` so the app can label the line; the server prices.
- **Driver side, paid by Movera.** `DriverAppConfig.pickupPay.byCategory[categoryId]: PickupPayRate { enabled, maxPerRide: Money | null, ranges: PickupRange[], riderFee }` with `PickupRange { fromKm, toKm: number | null, perKm: Money, perMin: Money }`. The first range starts at 0 (it may be free: rates 0), each next one starts where the one before ends, only the last may be open (`toKm` null). The pickup leg (from the driver's location when the offer is made; for a next trip while driving, from the current drop-off) is paid **tiered**: every km at the rate of the range it falls in, the minutes split across the ranges in proportion to the km in each (0 km: all the minutes in the first range), a leg beyond a closed last range at the last range's rate. Each range part is `half_up(km × perKm) + half_up(minutes × perMin)` in minor units; the parts add up, then `min(total, maxPerRide)`. `enabled: false` or a category not listed pays 0.
- **Which offers.** `pickupPay.offers { radar, exclusive, exclusiveReservation, assigned, nextTrip }` switches each kind; a reservation the driver took from the Scheduled rides list never gets pickup pay. Reservations offered as Exclusive, or in Radar near pickup time, are `exclusiveReservation`.
- **On the wire.** The server works the pay out when it makes the offer and sends `Offer.pickupPay`; the driver app shows the total only (`display: total`): the offer card's fare is `fare + pickupPay`, no breakdown. The accepted trip keeps it as `TripProjection.pickupPay` (driver and admin views; never in the rider's `fare`), and it is in `EarningsPeriod.pickupPay`. Money split: the rider pays `fare` (its `pickup_fee` line inside); the driver gets `driverEarnings + pickupPay + driverBonus`; Movera keeps `fare − driverEarnings − pickupPay − driverBonus`, and covers the difference when that is below 0 (the admin shows "Movera covers").
- **Defaults** (`contract.json#configDefaults.pickupPay`, placeholders until the owner sets the real amounts in Pricing): every offer kind on, display `total`, no maximum, the rider fee off with suggested amounts per country, the driver's first km free then the headline category's rate. The sample documents under `fixtures/config/` show the simplest state (fees `null`, no maximum, one range for every distance); `fixtures/pickup_pay.json` shows tiered ranges with a free first km, a fee and a maximum.
- **One release of compatibility.** The driver document keeps the v0.4 keys (`perKm`, `perMin`, `freeKm`, `freeMin`, top-level `ranges`, `maxPerRide`) filled from the headline category until v0.6; an app on the new shape ignores them. A v0.4 rider fare line coded `pickup_pay` is read as `pickup_fee`.

### 3.3 Offers while driving (v0.5.0, owner round 3)

The driver app decides **stopped / driving** from the device (`contract.json#driverMotion`): moving when the speed is at least `movingSpeedMps` (1 m/s) for `hysteresisSeconds` (10 s), stopped when below it for 10 s, so the state does not flicker at a traffic light. It sends the judgement as `GeoFix.moving` (and `speedMps`) in `POST /driver/location` and applies the limits itself at once; the server mirrors the latest value in `Driver.moving` (also on nearby-driver rows) and never sends more open offers than the limit of the driver's current state: an offer above it is held and sent when a slot frees, or dropped when it expires.

| Driver state | Full-screen Radar list | Offer cards over the map | Exclusive |
|---|---|---|---|
| No rider on board, stopped | up to `offers.radarApp.full` (when `fullOn`) | up to `offers.radarApp.popup` (when `popupOn`) | as today |
| No rider on board, moving | locked while `offers.radarApp.fullLockWhileDriving`; opens again once stopped | up to `offers.radarApp.popupWhileDriving` when `popupSplitByDriving`, else `popup` | as today |
| Rider on board | never Radar (Q18) | never Radar | only while `offers.exclusiveWhileDriving.on`, at most `count` at a time; cards never cover navigation |

Defaults (`contract.json#configDefaults.offers`): `radarApp { fullOn: true, full: 8, fullLockWhileDriving: true, popupOn: true, popup: 2, popupSplitByDriving: false, popupWhileDriving: 1 }`, `exclusiveWhileDriving { on: true, count: 1 }`. The owner's numbers for the test (N while stopped, M while driving) go in Admin Dispatch › Modes; they are not contract values. `offers.radarOn`, `offers.exclusiveOn` and `offers.assignAcceptSeconds` also travel in the driver document (the admin already exports them).

### 3.4 Surge schedule (v0.5.0)

An admin surge may change over its time like a speed curve (`contract.json#surge`, `SurgeSchedule`): `points [{ atMin, multiplier }]` from minute 0 to the end, straight lines between them, applied in `stepMinutes` (5) steps so the price never wobbles from one second to the next. The multiplier at a time is the curve's value at the start of the current step, rounded half-up to 0.1, never below 1.0 and never above the schedule's `cap` (set by the admin, at most `contract.json#surge.capMax` = 6 since v0.6.0) and the zone's pricing `surge.maxMultiplier` (§3.5); `null` before `startAt` and from `endAt` on (cases: `fixtures/surge.json`). The server prices new quotes from it; **a quote keeps the multiplier it was priced with** (`Quote.surgeMultiplier`, `Quote.surge { multiplier, until, scheduleId }` for display) whatever the schedule does next. One active schedule per zone and category (`categoryIds` empty = every category); a new one replaces it. A flat manual surge is a two-point curve with the same multiplier. Admin: `GET | PUT /admin/zones/{zoneId}/surge`, `POST /admin/zones/{zoneId}/surge/end`; points above the cap are `400 invalid_request`; since v0.7.2 it runs at once for every admin with `settings.publish`. Smart (automatic) surge stays server-side and is unchanged by this section.

Multi-stop: `stops[]` ordered on quote, request and projection; quotes MUST include stops. Waiting at a stop is billed per `pickupWait` rules. Route changes after request create a new quote (`/trips/{id}/route-quote`) and a `PATCH` with `expectedVersion`.

Route-change pricing (v0.4.3, owner decision 5). The route quote and the `PATCH` that applies it price the whole new route from the booking, never from the current fare alone:

- `total` = booked fare (the fare at request) + every offer raise the rider made while searching + the distance price of (new route km − booked route km) + the stop fee for each stop of the new route that was not booked. It is never below half of (booked fare + raises) and is rounded to the zone's price step.
- **Booked route** = pickup → booked stops, in order → dropoff: the route the booking quote priced. A booked stop is already in the booked fare, so a booked stop the new route keeps adds no kilometres and no stop fee. A stop of the new route within 50 m of a booked stop is that booked stop; each booked stop matches one new stop, once. A booked stop the new route drops gives back its kilometres (and its `stops` fare line, if the booking quote had one).
- **Offer raises stay.** A raise the rider made to find a driver is part of the price of every new route: a route change never cancels or refunds it. The offer ceiling is worked out again from the new total.
- `difference` = `total` − current `fare`; positive is charged, negative refunded (cash: only shown). Because `total` always starts from the booking, re-quoting the route the trip already has gives `difference` 0, successive changes do not add up, and going back to the booked route gives back what the changes cost.

After-cancel reason (v0.4.4, owner decision 6). A rider who cancels before picking a reason (cancel-first) names the placeholder `something_else`, because `CancelCommand.reasonCode` is required. The reason picked afterwards is sent with `POST /trips/{tripId}/cancel-reason {reasonCode, note?}` (rider only, `CancelReasonCommand`):

- Allowed only while the trip is `cancelled_by_rider` and its `cancellation.reasonCode` is still `something_else`. It sets `cancellation.reasonCode` to the given code, and `cancellation.note` when `note` is sent, and answers `200` with the TripProjection.
- `reasonCode` must be a rider code (`contract.json#cancelReasons.rider`); any other code is `400 invalid_request`. Any other trip state, also a trip whose reason was already told, is `409 invalid_transition` with the projection. Another rider's trip is `403 forbidden` or `404 not_found`, as for every trip command.
- It is not a lifecycle command and not in the transition table. Only `cancellation.reasonCode` and `cancellation.note` change: `status`, `version`, `sequence`, `updatedAt`, `fare`, `cancellation.fee`, `cancellation.actor` and `cancellation.at` stay as the cancel left them, and no realtime event is sent (after a terminal status the gate would block a `trip_projection` anyway). Apps read the new reason from the response and from `GET /trips/{tripId}` (admin: `GET /admin/trips/{id}`).
- It takes no `expectedVersion` (the state rule already makes it one-shot) and needs `Idempotency-Key` like every mutation: a repeat with the same key and body returns the first answer.
- A second `POST /trips/{tripId}/cancel` on a cancelled trip stays `409 invalid_transition` (the table) and never changes the reason.

Live free cancel: the `freeMin` of a live FeeRule counts from `acceptedAt` (owner Q12).

Scheduled rides: `kind = scheduled`, `scheduledAt` UTC. Free cancel until `freeCancelMinutesBeforePickup` (per zone × category, §5). Dispatch starts `searchBeforeMin` before pickup. A driver claim (`accept` from `requested`) can be released (`cancel` → `requested`). Since v0.5.1 the table says so in its own terms: `accept` from `offered` is one row and `accept` from `requested` another with `when: scheduled`, so a live trip in `requested` cannot be accepted (`fixtures/scenarios.json` `live_accept_only_from_offered`).

### 3.5 Fare (v0.5.1, owner decisions 5, 8, 16–21 (2026-10-24))

The server prices every quote and every fare from the zone's **pricing document** (§6.2), in the order of the admin panel's calculator (Pricing › Test a ride, `quoteRide`), with the owner's decisions applied (`contract.json#pricing`). Cases every price engine must reproduce: `fixtures/fares.json`. All amounts are exact (no rounding) until they become a fare line.

1. **Ride part.** A fixed route of the category (`fixedRoutes`) replaces it all: `fixed_route` = the route price, with no surge, minimum or maximum. Otherwise `base` + `distance` (perKm × km) + `time` (perMin × minutes).
2. **Surge** multiplies the ride part only: the `surge` line is ride part × (multiplier − 1). The multiplier is clamped to [1, 6] (v0.7.1: the maximum of each surge is the value the admin chose on its slider — manual surge, planned window, smart profile cap — and `surge.maxMultiplier` is deprecated and ignored; before: the zone's maximum, set by the admin from ×1 to ×6, v0.6.0, owner 2026-10-27, as in the admin demo; the Stockholm default is ×3). The maximum binds every source, smart surge included (smart surge also stays within its profile's `cap`). Where it comes from: the zone's surge schedule (§3.4), else a `surge.scheduled` window in force, else smart surge when `smart.enabled` (off in the test week); else 1.0. A quote keeps its multiplier.
3. **Minimum, then maximum** of the category, on the ride part after surge: `minimum_adjust` raises it to `minimum`; `maximum_adjust` (negative) lowers it to `maximum` when that is not `null`.
4. **Extras**, never surged: `waiting` (pickup waiting: `Waiting.chargedSeconds` / 60 × `waiting.perMin`, per second after the free wait), `stops` (`extraStopFee` per extra stop), `stop_waiting` (v0.7.1: no free minutes; per second at `stopWaitPerMin` from the driver's arrived-at-stop to leaving-stop, §3.8), `extras` (v0.7.1: a `child_seat` trip's one seat, `childSeatFee` once), `airport` (v0.7.1: `fees.airportPickup` when the pickup lies in a zone of kind `airport`, `fees.airportDropoff` when the drop-off does; the server decides), `reservation_fee` (`kind = scheduled`).

   **What the rider asks for** (v0.6.0, `contract.json#pricing.requestExtras`): `QuoteRequest` carries `babySeats`, `childSeats` (whole numbers 0–3, the admin calculator's limit), `airportPickup`, `airportDropoff` (booleans) and `fixedRouteId` (step 1); `CreateTripRequest` repeats them unchanged (else `400 invalid_request`, `quote_mismatch`), the trip keeps them and the fare at completion prices them again. Seat fees exist only on `child_seat` (owner 2026-10-27); as in the admin calculator (`quoteRide`), seats on a category without the fee add nothing. A `fixedRouteId` prices only the category the route belongs to; every other category is priced normally (the calculator's rule).
5. **App fee** = (ride part + extras) × `appFeePct` / 100: the `app_fee` line.
6. **Pickup fee**: the category's `riderPickupFee.live` (or `.reservation` for `kind = scheduled`) when not `null`: the `pickup_fee` line (§3.2).
7. **Total** = ride part + extras + app fee + pickup fee, rounded **once**, half-up, to a multiple of `priceStep` (1 kr in Sweden). Each line is its exact amount rounded half-up to a whole minor unit; a `rounding` line (total − the sum of the rounded lines, may be negative) makes the lines add up, and is left out when it is 0. Half-up means a tie goes up (toward +∞), also on a negative line.
8. **Outstanding fee** (§3.7): while the rider owes one, the `outstanding_fee` line is added after the rounding; `Quote.total` and `fare` include it.

**Money split** (owner decisions 16–18). Commission base = ride part + extras − waiting − stop waiting: no commission on waiting (decision 17), and the app fee and pickup fee are Movera's and outside it (decision 18). `driverEarnings` = half-up(commission base × (1 − `commissionPct` / 100)) + the `waiting` and `stop_waiting` lines, never more than the total before `outstanding_fee`. Movera's share = `fare` − `driverEarnings` (the app fee, the pickup fee, the commission, the rounding and any outstanding fee); `TripProjection.commission` carries it. Premium keeps the panel's 22 % commission and 12 % app fee, every other category 20 % and 10 % (decision 16). Driver pickup pay and driver bonus come out of Movera's share as before (§3.2).

**Quote and fare.** The quote prices the server's own route (OSRM km and minutes, §10; a distance a client sends is a hint) with no waiting. The fare at completion is the same calculation with the quote's km and minutes, the stops made and the waiting the trip had, rounded once. Route changes keep the v0.4.3 rule (§3 "Route-change pricing").

**Rider ends the trip early** (`end_early`, owner decisions 8 and 19): ride part = base + km driven × perKm + minutes on board × perMin, × the booked surge multiplier, then the minimum and maximum; no extras; then the app fee and the pickup fee. When that is above the booked fare (the quote total plus route changes, without the outstanding fee), the ride part is lowered (`maximum_adjust`) so that ride part + app fee + pickup fee is exactly the booked fare; the total is then rounded once to the price step. `driverEarnings` follow that ride part.

**Driver ends the trip early** (v0.18.1, owner decision 28, `contract.json#pricing.driverEndsEarly`): when the driver completes and their latest fix (`POST /driver/location`) is farther than `completeNearDropoffMeters` (300 m) from the drop-off, the trip ended early and is priced exactly as the rider's end early above (km on board from the trace, minutes since boarding, the category minimum and maximum, never more than the booked fare). Within 300 m, or with no fix, the booked fare stands plus the waiting at middle stops. An admin's force-complete fare is taken as given. The driver app shows this price before collecting cash (§26).

**Not in the formula** in v0.5.1: `cleaningFee` (charged afterwards with `POST /admin/trips/{id}/adjust`), `tollsPassThrough` (no tolls are priced), the smart surge algorithm (kept in the document, off in the test week), promotions (`discount`, hidden in the test week).

### 3.6 Automatic dispatch (v0.5.1, owner decisions 6, 10, 22–24 (2026-10-24))

How the server finds a driver for a live trip in `searching`, from the **pickup zone's** dispatch document (§6.3) and its live `DispatchControl`, as the admin panel's rules describe it (`modeNow`, `rankDrivers`, `simulate`). Constants, ranges and the full rule list: `contract.json#dispatch`; timelines every dispatcher must reproduce: `fixtures/dispatch.json`. Time `t` counts from search start (the trip enters `searching`).

- **Mode at search start**, first match: the zone is paused → no automatic offers; a forced mode (`control.mode`); the first time rule that is on, whose mode is on and whose zone-local window `[from, to)` holds now (it wraps midnight); `start.mode` when it is not `auto` (v0.18.11: `radar`, `exclusive`, `byDistance` = Exclusive first when the nearest not-yet-asked driver in range (smallest km, not the top score) is within `start.nearKm`, else Radar; `both` = an Exclusive offer to the best driver and a Radar round to the next `radar.drivers` at the same moment, first accept wins, the others withdrawn, then the search goes on as Exclusive, and a driver who had that first Radar offer may still get an Exclusive later); `choose.how = auto` with both modes on → Radar when busy ≥ `radarAbove`, else Exclusive; else `choose.main` when on, else the mode that is on. Busy = waiting trips in the zone (`requested`, `searching`, `offered`, the new one included) ÷ max(1, free online drivers in the zone), rounded to 0.1, worked out once. `choose.backup` (deprecated, optional) and `rulesFrom` are ignored (the next steps follow `then`). v0.18.11 options, all optional with today's behaviour when missing: `radar.steps` / `exclusive.steps` (that mode's own search steps, else `radius.steps`), `limits { maxPickupKm, maxPickupEtaMin }` (0 = off), `neighbours { on, zoneIds, afterStep }` (drivers of those zones from that step; only zones with the pickup zone's country and currency, others ignored). The two step lists may differ in length (step i uses `steps[min(i, len-1)]` of the offering mode); `maxPickupKm` is capped at the widest step (a larger value has no effect); `maxPickupEtaMin` uses the approximate ETA km ÷ 24 km/h (`pickupKmh`), not the routing service — `contract.json#dispatch.start`, `modeSteps`, `limits`, `neighbours`.
- **Who and in what order**, ranked again before every offer: drivers who may take it (the category, within the widest radius step, and a driver on a ride only when finishing within `finishing.withinMin` and `withinKm`), then score high to low, then km, then `driverId`. Distance is the straight line × 1.25 (`roadFactor`), ETA at 24 km/h (`pickupKmh`). The score is the admin's: each factor that is on gives round(weight ÷ the sum of the on weights × 100 × its ratio, the ratio kept within 0..1): ETA 1 − min/20, rating (rating − 3.5)/1.5, acceptance %/100, cancel 1 − %/30, waited min/30, finishing nearby 1, rider's favourite 1 (within `favourite.maxKm`). A driver with no data counts as rating 4.7, acceptance 85 %, cancels 5 %. Radar never goes to a driver with a rider; Exclusive does only while `finishing.exclusive` and `exclusiveWhileDriving.on`.
- **Radar round**: the trip is shown at once to the top `radar.drivers` within the current radius step for `radar.seconds`; the first to accept wins, the others get `offer_withdrawn` (`claimed_elsewhere`). Nobody is marked as asked, so a driver who declined or let it run out may see it again on a later round (owner decision 23).
- **Exclusive**: one driver at a time, the best within the step who was not asked yet, for `exclusive.seconds`, at most `exclusive.drivers` per step. A driver is asked once per search; a decline moves on at once. Reason line (`Offer.reasonCode`): `favourite`, else `finishing-nearby`, else `best-match` for the top-ranked driver, else `nearby`.
- **What comes next** (`then`): after a Radar round nobody took, widen (`widen`, `widen_then_exclusive`) while a wider step exists; else switch to Exclusive at the same step (`exclusive`, `widen_then_exclusive`) once; else widen. After an Exclusive step, widen (`widen`, `widen_then_radar`); else switch to Radar (`radar`, `widen_then_radar`) once; else widen. The start mode does not count as switched into, so a search can go back to it once. A round with nobody in range moves on at once.
- **When the steps are used up** before the search ends (owner decision 22, approved as "Radar every 15 s at the widest area, and Exclusive to any driver not yet asked"), the search never goes silent. Each repeat round at the widest step is: when `exclusive.on` and a driver in range has not been asked on Exclusive in this search (newly free drivers count), an Exclusive offer to the best such driver for `exclusive.seconds`; otherwise, when `radar.on`, a Radar round to the top `radar.drivers` in range for `radar.seconds`; otherwise the server waits `radar.seconds` (`exclusive.seconds` when Radar is off) and looks again. Rounds go on until the search end (`fixtures/dispatch.json` `thin_zone_chain_ends_in_exclusive`).
- **Search end** = the first of `radius.maxWaitMin` and the first `busy` step that is on. No offer starts at or after it, and `Offer.expiresAt` = min(sent + seconds, search end). At the end the trip takes `expire` (`expired`, "no driver found").
- **Rider-waiting steps**: every step that is on, by `afterMin` from search start; `raise_price` and `upgrade` are skipped in the test week (owner decision 10). A step that fires before the search end becomes `TripProjection.searchStep { id, kind, message, extraMin, at }` (rider view, sent as `trip_projection`; it does not change `version`). `alert_admin`: the trip shows in Live with an alert and offers go on. `keep_waiting`: the rider app asks "Keep waiting? / Stop" and answers with `POST /trips/{tripId}/keep-waiting { answer, expectedVersion? }`: `wait` adds `extraMin` minutes to the search end and a `busy` step that has not fired moves to no earlier than the new end; `stop` is the normal free rider cancel (`cancelled_by_rider`, reason `wait_too_long`, no fee: no driver accepted); no answer, the search goes on (owner decision 24). The command is allowed only while the trip is `searching` or `offered` with an unanswered `keep_waiting` step; else `409 invalid_transition`. `busy`: the search ends with the step's message. **Raising the offer** (v0.5.5, owner decision 25): the rider's `POST /trips/{tripId}/raise-price { expectedVersion, increase }` while `searching` or `offered` (transition `raise_price` → `searching`): `fare` += `increase` as a `rider_raise` line, `driverEarnings` += `increase` (Movera's share unchanged), open offers are withdrawn and a new search starts in which the drivers who already declined are asked again at the new price; `version` + 1. The new fare may not pass `dispatch.raisePrice.maxFactor` × the quoted fare (`400 invalid_request`, reason `raise_too_high`); another currency is `400 invalid_request` (`currency_mismatch`).
- **Live switch** `DispatchControl { zoneId, paused, mode, by, at, version }`, `PUT /admin/zones/{zoneId}/dispatch-control { expectedVersion, paused, mode, note? }` (`dispatch.edit`): pausing stops new offers, also in searches already running (open offers run out), while the waiting steps and the search end keep running so riders are not stuck; a forced mode applies to new searches; forcing a mode that is off is `400 invalid_request` (`mode_off`). Pausing, forcing a mode, resume and back to the rules apply at once for every admin with `dispatch.edit` (v0.7.2, one admin is enough).
- **One search per driver cancel**: a driver cancel that puts the trip back in `searching` starts a new search (new `t = 0`, new steps); the driver who cancelled stays asked. A free driver holds at most one open Exclusive, a driver with a rider at most `exclusiveWhileDriving.count`; Radar deliveries keep the §3.3 limits.
- **Timers agree.** `DriverAppConfig.offers.radarSeconds`, `exclusiveSeconds`, `radarOn`, `exclusiveOn` (and `exclusiveWhileDriving`) must equal the same zone's dispatch document; the admin builds both from Dispatch › Modes (`contract.json#configDocs.mustMatch`).

### 3.7 Unpaid cash fees (v0.5.1, owner decision 7 (2026-10-24))

Cash only in the test week: a cancel or no-show fee the rider does not pay at once puts their account in minus.

- The trip's `cancellation.feeStatus` is `owed` (else `paid` or `waived`), and `Rider.outstanding` (on `GET /rider/profile` and the admin rider view) is the sum of what the rider owes; `null` or missing means nothing.
- While it is open, every quote and the next trip carry it as the `outstanding_fee` line (`FareLine.sourceTripId` names the trip that owes it), added after the price-step rounding (§3.5); `Quote.total` and `TripProjection.fare` include it, so the rider sees one higher total with its own line.
- It is cleared (`feeStatus` `paid`) when a cash trip that carries it completes and is paid. A trip that carried it but did not complete leaves it owed.
- The driver of the original trip gets their share at once (an earnings entry: `EarningsPeriod.fees`; the no-show share is `waiting.driverSharePct`), paid in Movera's regular payout; Movera carries the risk.
- On the next trip the line is cash the new driver collects (in `cashCollected`) but it is **not** in their `driverEarnings`: it is owed to Movera with the rest of the driver's cash balance.

## 4. Realtime and synchronisation

Envelope (`contract.json#realtime`): `eventId, tripId, sequence, version, kind, occurredAt, serverTime` + optional `projection, location (GeoFix), etaSeconds, cancelFee (Money|null), message (Message, only for kind=message), eta (TripEta, v0.18.7, on the ETA tick's location event)`. v0.18.7 adds the kind `pickup_moved` (the rider moved the pickup; carries the projection, before terminal only). In `fixtures/events.json`, top-level `status`/`paymentStatus`/`ratingStatus` are test shorthand for the same fields in `projection`.

- `sequence` is **server-assigned**, contiguous per trip. Clients never number events.
- Gate (same in all apps; cases in `fixtures/events.json`): invalid if `sequence < 1` or blank `tripId`; duplicate if `eventId` seen or `sequence ≤ last`; gap → accept and resync; after a terminal status only `payment_updated`, `rating_updated`, `message` pass; `location` never replaces the projection.
- Kinds: `trip_projection, rider_cancelled, driver_cancelled, location, driver_arrived, rider_on_the_way, payment_updated, rating_updated, message`.
- `rider_on_the_way` is raised by the rider's `POST /trips/{tripId}/on-the-way` (v0.5.4); the other kinds come from the server's own commands and changes.
- Transport: `GET /trips/{tripId}/events` (SSE or WebSocket), replay with `?after={sequence}`. Fallback: poll `GET /trips/{tripId}` (projection carries `sequence`).
- Driver offer feed: `GET /driver/offers/stream` with `offer_created`, `offer_updated`, `offer_withdrawn` (status `claimed_elsewhere | expired | withdrawn`), each with a per-driver `sequence` for replay (`?after=`). A driver decline (`POST /offers/{id}/decline`) makes the system run `offer_lapsed`.
- Config: `config_published` on `/rider/config/stream` and `/driver/config/stream`; apps then re-fetch the config document.
- Admin: list endpoints with cursor paging + the same trip event stream for the live map. Incidents: `GET /admin/incidents/stream` (v0.7.0, §15).

### 6.1 `DriverAppConfig.reservations`

Built by Admin from Dispatch › Reservations of the zone. Every field is optional on read: a missing or invalid field keeps the driver app's default, which is `contract.json#configDefaults.reservations` (the values below).

```
DriverReservations {
  on: true,                     // reservations for every driver in the zone (= features.scheduledRides); off: no new ones, accepted ones still run
  lateWarn: true,               // "Head to your 07:40 pickup" island warning when Leave now cannot start
  offlineBackupAfterMin: 5,     // 1–60. Only an OFFLINE driver loses the ride this long after Leave now; an online driver keeps it
  homePopupAfterMin: 10,        // untaken: Home popup this long after booking
  exclusiveBeforeMin: 20,       // untaken: Exclusive from this long before pickup
  radarBeforeMin: 15,           // untaken: Radar trips from this long before pickup
  onDriverCancel: "byTime",     // byTime | list | home | exclusive
  hideClashing: true,           // rides that do not fit the smart gap leave the driver's list once they take one
  towardPickup: true, towardPickupBeforeMin: 60,
  longTripKm: 50,               // a ride longer than this is a longTrip
  driverLateCancelHours: 1,     // a driver cancel closer to pickup is a late cancel
  lateCancelLimit: 2, lateCancelPeriodDays: 7, pauseDays: 7,   // limit late cancels in the period → no scheduled rides for pauseDays
  assignAcceptSeconds: 30,      // time to accept a ride assigned by Movera
  rideTypes: { normal | airport | longTrip | comfortPremium | event:
               { onlineBeforeMin, spareMin, reminderMin: [int] } },  // defaults 30/60/60/45/45, spare 15, reminders [60, 15]
  lateEta: { on: true, toleranceMin: 3, checkEverySeconds: 60, reassignTo: "exclusive" } }
```

- **Leave now** fires at the driver's estimated drive time to the pickup + `rideTypes[kind].spareMin` before pickup (an estimate, not live traffic). It always opens the trip, heading to the pickup; there is no switch for it (v0.4.2, owner decision 1). When the trip cannot open at that moment (the driver is offline, or another screen or an offer answer is in the way), the `lateWarn` warning shows and the trip opens as soon as it can. A `leaveNow` field in an older document is ignored.
- **Running late (`lateEta`)**: from Leave now until the driver arrives at the pickup, the driver's ETA is checked every `checkEverySeconds` (15–600). When `now + ETA > pickup time + toleranceMin` (`toleranceMin` 0–30), the ride is reassigned early to `reassignTo`: `exclusive` (Exclusive offer to the nearest available driver), `radar` (Radar trips) or `dispatch` (back to admin dispatch). Otherwise an online driver keeps the ride.
- **Offline driver**: only a driver who is offline at Leave now loses the ride, after `offlineBackupAfterMin`. An online driver is never removed by that timer.
- **Reservations on/off (owner decision 2)**: a driver gets new reservations (Scheduled rides requests, the Home popup, Exclusive and Radar reservation offers, rides Movera assigns) only while the zone's `reservations.on` (and `features.scheduledRides`) is true **and** their `Driver.scheduledRides` does not turn them off. Off, for the zone or for the driver, the app lists no open requests and shows no reservation offer, and the backend offers and assigns none to that driver. Reservations the driver already accepted stay theirs and run as usual: reminders, Leave now, the ETA watch, cancel.
- `Driver.scheduledRides { on: bool, until: Timestamp | null }` (on `GET /driver/profile`): the admin's choice for this one driver. Missing = no choice (the zone switch and the late-cancel pause decide). `on: false` = no new reservations until `until` (null = until an admin turns them on). `on: true` = on until `until`, and the late-cancel pause is skipped while it lasts. A zone that is off wins over `on: true`.
- Admin ids map: `normal → normal`, `airport → airport`, `long → longTrip`, `premium → comfortPremium`, `event → event`; Admin `lateBackupAfterMin` is `offlineBackupAfterMin`.

Cancel reasons: the rider document lists `{code, title}` in the rider's language; the driver document lists codes per group and the titles come from `texts`. Unknown keys are ignored; missing keys fall back to the app's seed.

**Document version** (v0.8.0, `contract.json#configVersion`): the **server stamps** `version` and `publishedAt` when it publishes (whatever the admin sends there is ignored); `version` is strictly increasing per zone and document as the apps see it, also when a zone goes from its country's standard to its own document (§6.4). The server stores the published document as the admin built it (with the stamps, the zone id and, for a standard, `usesStandard`) and serves it from `GET /rider/config` and `GET /driver/config`; `config_published` carries the same `version`. Apps keep the last good document and ignore an older version. The same rule holds for the server-only `pricing` and `dispatch` documents (v0.5.1), which the apps never get.

### 6.2 `PricingDocument` (v0.5.1, server-only)

Built by Admin from Pricing (the zone's price set, `zonePricing.ts` `ZoneBook`), published with `PUT /admin/config/pricing` + `POST /admin/config/pricing/publish` and the same version rule; only the server's quote engine and admins with `settings.read` read it (`GET /admin/config/pricing?zoneId`). `GET /rider/config` and `GET /driver/config` never include it and no `config_published` is sent for it. ### 6.4 Country standard (v0.8.0)

`contract.json#configDocs.standard` and `#configDocs.scope`. Every country (SE in kr, FR in €, TN in DT) has one standard of each of the four documents, set in the admin with `GET|PUT /admin/config/{doc}?country=SE` and `POST /admin/config/{doc}/publish { country }` (exactly one of `zoneId` or `country`). A standard carries `zoneId: "standard-SE"` and the country's currency, country and time zone.

- A zone with **no own published document** of a kind uses its country's standard of that kind: the apps get it from `GET /rider/config` / `GET /driver/config` with the zone's id and `usesStandard: true`, and the server prices (pricing) and dispatches (dispatch) with it. The admin shows such a zone as **"Uses standard"**; `GET /admin/config/{doc}?zoneId` answers `usesStandard: true` with the standard as the starting draft.
- A zone **with its own published document never uses the standard** again.
- Publishing a standard sends `config_published` for every zone of the country that uses it. A zone's first own publish gets `version` = max(its own live, the standard's live) + 1, so the apps never see a lower number.
- **Go back to Standard** (`contract.json#configDocs.useStandard`): `POST /admin/config/{doc}/use-standard { zoneId, expectedVersion }`, after the admin confirms, removes the zone's own document (kept in the history) and the zone uses the standard again; the server re-stamps the standard above the zone's last own version so its apps never see a lower number.
- Any admin who covers at least one zone of the country and holds the document's permission may edit and publish its standard.
- Seeds (`fixtures/config`) are only for development and staging; production has no seeds: a country with no standard and a zone with no document has no prices (`pricing_not_published`) and no automatic dispatch until the admin publishes.

### 6.5 Tips & limits — country rules (v0.8.0, per zone since v0.8.1)

`contract.json#configDocs.countryRules`. `CountryRules { version, publishedAt, country, currency, tips, raiseSteps, driverBonus }`. **v0.8.1 (owner 2026-10-28): Tips & limits apply only to the zones chosen at the top; for the whole country the admin chooses "All zones".** Like the other documents it is published for a zone (`?zoneId`, the zone's own) or for a country (`?country`, the standard); a zone with no own rules uses the standard ("Uses standard"), and "Go back to Standard" (`use-standard`) works for it too. Publishing a zone's own rules writes `RiderAppConfig.tips` / `raiseSteps` and `DriverAppConfig.driverBonus` into that zone's live and draft app documents (a zone on the standard app documents gets its own, copied from the standard with the new values), each changed one as its next version with `config_published`. Publishing the standard rules writes them into the standard app documents and into the own app documents of the zones with no own rules. While rules are live, a PUT or publish of a zone's app document keeps these three fields from the zone's rules; the driver bonus limit of a trip is its zone's.

### 6.6 Booked trips keep their rules (v0.8.0)

`contract.json#bookingSnapshot`. At `POST /trips` the server keeps on the trip everything that decides money later: the pricing document (version and whether it was the zone's or the standard), the category's cancel fee rule (`cancelFees.live` or `.reservation` by `Trip.kind`), `DriverAppConfig.cancelFees.driverSharePct` (default 100 %), the category's waiting terms and no-show fee, and the no-show and waiting driver shares. `contract.json#autoOffline`. After `offers.autoOffline.missedExclusive` (default 10) **Exclusive or hand-sent (assigned)** offers of live trips in a row that the driver declined or let expire, the driver goes offline (v0.18.6, owner G4-E3 "Count them": hand-sent offers count too; G4-E2 "Set 10 everywhere": the server migration set every zone still on another limit to 10). ## 8. Sign-in, tokens and push devices (v0.5.0)

`contract.json#auth`. The rider and driver apps sign in the same way; the admin signs in with e-mail, password and a second factor, outside this contract (v0.5.1: the admin's sign-in is now §9, e-mail and password without a second factor for the test week). No bearer token on the four sign-in calls.

- **Phone + SMS code.** `POST /auth/otp/request { phone (E.164), app: rider | driver, linkToken?, locale? }` → `{ requestId, sessionId, expiresAt, retryAfterSeconds }` (code 4 digits, 300 s, resend after 30 s, 5 attempts; rate limited per phone and device, `429 rate_limited` with `Retry-After`). `POST /auth/otp/verify { phone, sessionId, code, linkToken? }` → `AuthTokens { accessToken, refreshToken, expiresIn, actor, isNewRider?, isNewDriver? }`. A wrong code is `400 invalid_request` (`reason: invalid_otp_code`), an unknown session `400` (`invalid_otp_session`), an expired code or session `410 otp_expired`, too many attempts `429`.
- **Apple / Google.** `POST /auth/provider { provider: apple | google, idToken, app, name? }` → `AuthTokens` for a linked account, or `{ code: "PHONE_REQUIRED", linkToken, firstName?, lastName?, email? }` for a new one: the app then verifies a phone with that `linkToken` on the OTP calls (the phone is confirmed once, the first time; afterwards Apple / Google alone signs in) and the account is created linked to the provider; the driver app prefills its details step with the names and e-mail the provider gave (Apple gives them only the first time and may give a hidden relay e-mail; all stay editable). The server verifies the token against the provider's public keys and its own client ids (`contract.json#auth.providerKeys`: `APPLE_CLIENT_IDS`, `GOOGLE_CLIENT_IDS`); while a provider's keys are not set it answers `503 unavailable` (`reason: provider_not_configured`) and the apps show the button as coming soon.
- **Tokens.** The access token is a short-lived JWT (900 s) carrying actor, subject id, zone scope and, for admins, role and permissions. The refresh token is opaque, lives 30 days and is **rotated** on every `POST /auth/refresh { refreshToken }` → `AuthTokens`; a used, revoked or unknown one is `401 unauthenticated` and the app signs out. `POST /auth/sign-out` revokes the session (idempotent, `204`).
- **Test numbers (outside production only).** The staging server seed lists the test group's phone numbers; an OTP request for one of them sends no SMS and the fixed code (`contract.json#auth.testSignIn.code`, placeholder `1234` until the owner sets one) signs it in. Production has no test numbers.
- **Push devices.** `POST /push/devices { token, provider: fcm | apns, platform: ios | android | web, appVersion?, locale? }` → `{ status: registered }`, keyed by token and actor (registering again updates it); `POST /push/devices/unregister { token }` on sign-out. Push is off during the first test week (the driver app stays open); the registration still happens so it can be switched on without an app change. v0.18.3 (R7): sending is on when the server has its Firebase service account (§28).

## 9. Admin sign-in (v0.5.1)

`contract.json#auth.admin`, owner decisions 9 and 14 (2026-10-24). One Super admin, the owner's e-mail, set on the server and not in git. No bearer token on sign-in, setup and refresh; these are separate from the rider and driver `/auth/*` calls.

- **Sign-in.** `POST /admin/auth/sign-in { email, password }` → `AdminSession { accessToken, refreshToken, expiresIn: 900, actor: "admin", admin: AdminMe }`. An unknown e-mail, a wrong password and a deactivated account all get the same `401 unauthenticated` with reason `invalid_credentials`. Failed attempts are slowed, then locked: `429 rate_limited` with `Retry-After`. A later second factor will be added as a `{ code: "SECOND_FACTOR_REQUIRED", … }` answer; that code is reserved and never sent in v0.5.1.

The password has at least 10 characters (else `400 invalid_request`, `weak_password`) and is stored as argon2id. An unknown token is `400 invalid_request` (`invalid_setup_token`); an expired or used link is `410 otp_expired` (`setup_link_expired`, `setup_link_used`).
- **Tokens.** The access token (900 s) carries actor `admin`, the admin id, role, expanded permissions and zone scope. `POST /admin/auth/refresh { refreshToken }` → `AdminSession`, rotated every time, at most 12 h; a used, revoked or unknown token is `401`. `POST /admin/auth/sign-out` revokes the session (`204`, idempotent). The panel signs out by itself after `idleTimeoutSeconds` without use (default 900, 5–240 minutes on the Team page).
- **Who.** `GET /admin/auth/me` → `AdminMe { adminId, email, name, role: AdminRole, permissions: AdminPermission[] (fully expanded), scope: { zones: "all" | ZoneId[], countries?, fleetPartnerId? }, language?, idleTimeoutSeconds, approvalExempt }`; it maps one to one onto the panel's agent (`adminId` = `id`). v0.17.1: `PATCH /admin/auth/me { language }` (`en`, `fr`, `sv` or `null` to clear) saves the admin's own panel language and answers the updated `AdminMe`; any signed-in admin, no permission id; audited; another value is `400 invalid_request`.
- **Permissions.** `AdminPermission` is the panel's 34 ids (`contract.json#adminPermissions`): look `overview.read, trips.read, riders.read, drivers.read, zones.read, finance.read, incidents.read, audit.read, team.read, system.read`; private data `riders.viewSensitive, drivers.viewSensitive`; act `trips.annotate, trips.intervene, support.reply, safety.edit, riders.block, riders.promotions, drivers.activate, drivers.bonuses, documents.approve, vehicles.edit, alerts.manage, payments.refund, finance.edit`; setup `zones.edit, zones.publish, dispatch.edit, dispatch.approve, settings.read, settings.edit, settings.publish, approval.decide, team.edit`. Every admin operation's `x-permission` in `openapi.yaml` is one of them; where v0.5.0 named another value it is kept as `x-permission-v050` (`trips.edit` → `trips.intervene`, `payments.edit` → `payments.refund`, `config.edit` → `settings.edit` / `settings.publish`, `pricing.*` → `settings.read` / `settings.publish`, and so on). `PUT /admin/config/{doc}` and its publish name the permission per document in `x-permission-by-doc` (dispatch rules: `dispatch.edit`, approved with `dispatch.approve`).
- **Super admin** (`super`): every permission, `approvalExempt: true`; their refunds, publishes and other big changes run at once (`200`, never `202`) and are written in the audit (owner decision 14, §3.1).

## 10. Locations and routes (v0.5.1)

`contract.json#maps`, owner decision 4 (2026-10-24): address search goes through the server (Google Places / Geocoding; the server keeps the provider's session tokens and a cache), routes, distances and arrival times come from Movera's own OSRM. All of these are read-only: no `Idempotency-Key`.

v0.18.4 (extended): owner decision G3-D3 ("Search + his recent"): the driver app's destination mode searches any address, so `POST /locations/autocomplete` and `/locations/geocode` take the `driver` actor as well as `rider` (same rate limits; `/locations/reverse-geocode` already took both). Provider session tokens are kept per actor and account.

- `POST /locations/autocomplete { query, latitude?, longitude?, limit: 8 }` (rider, driver) → `{ suggestions: [{ title, subtitle?, latitude?, longitude?, placeId? }] }`; the point biases the search; an empty list means nothing was found. A suggestion without coordinates is resolved with geocode.
- `POST /locations/geocode { query, placeId? }` (rider, driver) → `{ address?, name?, latitude?, longitude?, placeId? }`; no coordinates means no match (`200`, never `404`). v0.18.44 §67: a picked suggestion is resolved by its `placeId` and `name` is the place's own name.
- `POST /locations/reverse-geocode { latitude, longitude }` (rider, driver) → `{ address: string | null, latitude, longitude }`, in the caller's profile language (or `Accept-Language`). Bad coordinates: `400 invalid_request` (`invalid_coordinates`).
- These three bodies say `latitude` / `longitude` (§1, the only exception).
- `POST /routes { mode: driving, from: { lat, lng }, to: { lat, lng }, via?: [{ lat, lng }] }` (rider, driver; `via` since v0.18.41 §66) → `RoadRoute { points: [{ lat, lng }], distanceMeters?, durationSeconds?, provider? }`; no route is `404 not_found` (`no_route`), and the app draws a straight line. The rider's ETA stays `TripProjection.etaSeconds`.
- `GET /routes/driving/{coordinates}` (driver navigation): OSRM's own path syntax (`lng,lat;lng,lat`, 2 to 10 points) and query (`overview`, `geometries=geojson`, `steps`, `annotations`, `alternatives`); the answer is the OSRM v5 route response passed through (`{ code: "Ok", routes, waypoints }`), of which the contract names the subset the driver app reads (`OsrmRouteResponse`). No route is `200 { code: "NoRoute", routes: [] }`; auth and rate errors are the normal `Error`; about 30 calls per minute per driver.
- The server routes quotes itself: a distance or duration a client sends with a quote is a hint and is never priced (§3.5).

## 11. Telemetry (v0.5.1)

`contract.json#telemetry`. `POST /telemetry/logs { level: debug | info | warning | error | fatal, event, extra?, error? }`, `POST /telemetry/analytics { event, extra? }`, `POST /telemetry/crashes { error, stack?, extra? }` from any app: no bearer token needed (one is used when sent), no `Idempotency-Key`, `X-Request-Id` and `X-Api-Version` optional. The answer is `202` with an empty body; the apps do not wait for it. A body is at most 16 KB (else `400 invalid_request`, `payload_too_large`); calls are rate limited per address and device (`429`). The apps scrub e-mails, phone numbers and coordinates; the server scrubs again and keeps the data 30 days.

**v0.16.0: Crashes & errors** (owner 2026-10-29: "Want section on dispatch to show all crash droids and bugs detected from server is that poss"; who may mark fixed: "No code now every one can see and later we add"; who may see it: "All admin roles (Recommended)").

- **Report.** `POST /telemetry/crashes` also takes, all optional: `app` (`driver` | `rider`), `platform` (`android` | `ios` | `web`), `appVersion`, `build`, `screen` (route or screen name, no ids), `kind` (`crash`: the app stopped, the default; `error`: caught and shown) and `occurredAt`. An app that sends none of them still works. Nothing else changes: no bearer token needed, `202`, same size limit, rate limit and scrubbing.

The server's own unhandled `5xx` errors are recorded too, as app and platform `server`, scrubbed the same way. At most 200 reports are kept per group (the count goes on); reports are kept 30 days.
- **Admin.** `GET /admin/errors?app=&platform=&version=&status=&cursor=&limit=` → `ErrorGroupPage`, newest `lastSeen` first. `PATCH /admin/errors/{errorId} { status: open | fixed }` → `ErrorGroup`, audited. ## 14. Driver sign-up, fleets and documents (v0.5.3)

`contract.json#driverOnboarding`, owner decisions of 2026-10-25. The driver app signs in like the rider (§8: phone and code, or Apple / Google followed by the phone the first time) and the details screen is the sign-in's last step. `AuthTokens.isNewDriver` and `Driver.accountStatus = pending` both mean the details screen comes next.

- **Account types** (`DriverAccountType`): `driver`, who works for a fleet and is paid through it; `fleet`, a company (taxi company in Sweden, exploitant VTC in France) that owns the cars and has drivers, whose owner may drive too.
- **Details, once.** `POST /driver/onboarding { firstName, lastName, dateOfBirth, email, country, cityId, language, accountType, termsAccepted: true, company?, fleetJoin? }` → `Driver`. `country` is one of `SE`, `FR` (open) or `TN` (listed, not open: `400 invalid_request`, `country_not_open`); `cityId` one of the country's cities (`stockholm_lan` → zone `Z001`, `paris` → `FR-PC`), which sets `zoneIds`; the driver is at least 21 (`minAge`, else `under_age`); `termsAccepted` must be `true` (`terms_required`; stored as the `terms` document, approved, `Driver.termsAcceptedAt`); a `fleet` account sends `company { name, orgNumber, address }` (`company_required`) and gets a `Fleet` in status `pending`; a `driver` account may send `fleetJoin` to join a fleet at once. Allowed while `accountStatus` is `pending` or `on_hold` (a resend replaces the details); afterwards `409 invalid_transition`. It moves `pending` → `on_hold`.
- **Account status** (`contract.json#driverOnboarding.accountStatus`): `pending` = signed in, no details yet; `on_hold` = details sent, waiting for Movera (the app opens; the driver uploads documents and sees the hold; going online is `409 invalid_transition`, `account_not_active`); `active` = an admin approved (`POST /admin/drivers/{driverId}/status`, `drivers.activate`), when the person's required documents are approved; `suspended` = blocked. **v0.14.0** (owner 2026-10-28, `contract.json#driverOnboarding.activation`): activation and car approval are separate. The server refuses `active` with `409 documents_not_approved` unless every required document has status `approved` (kinds `acceptance` and `admin_check` included): a driver attached to a fleet needs his `Driver.requiredDocuments`; a fleet owner (also a driver who drives his own car; a fleet may have one car) needs `Driver.requiredDocuments` and `Driver.requiredFleetDocuments`. No car is needed, and a missing car never puts an account on hold. `details` lists what is missing as `<scope>:<type>` (`driver:info_session`, `fleet:company_registration`). Approving a fleet (`POST /admin/fleets/{fleetId}/review`) is separate from activating its owner as a driver.
- **Fleet code.** The first approval of a fleet makes its code: `MV-` + 5 characters of `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (no 0 / O / 1 / I), case-insensitive on entry. Only the owner (`GET /driver/fleet`) and admins see it. `POST /admin/fleets/{fleetId}/code` makes a new code and the old one stops working at once.
- **Joining is an invitation** (`contract.json#driverOnboarding.fleetInvitations`, `FleetInvitation`, owner decision of 2026-10-25): one side asks, the other accepts; nothing links a driver without both. A driver asks with `POST /driver/fleet/join { code, ownerName, ownerEmail }` (or `fleetJoin` on onboarding) → `201 FleetInvitation` (`direction: driver_request`, `pending`): the code, the owner's first and last name and the owner's e-mail must all match one approved fleet (case and spaces forgiven); any mismatch is `400 invalid_request` with the one reason `fleet_join_mismatch`, so nothing tells which part was wrong; at most 10 tries per hour per driver (`429`); one open request at a time (`409 conflict`, `request_pending`). The owner invites a phone number with `POST /driver/fleet/invite { phone }` → `201 FleetInvitation` (`owner_invite`): a driver with that number gets it at once; a number without an account gets it the moment someone signs up with it (`driverId` missing until then). Both sides list theirs with `GET /driver/fleet/invitations`; `FleetView.invitations` carries the fleet's for the owner and admins; `Driver.pendingFleetInvitations` counts the ones waiting for this account's answer (the badge on Home and My fleet). The receiving side answers with `POST /driver/fleet/invitations/{invitationId}/accept|decline`; the sender takes its own back with `.../cancel`; an admin may `POST /admin/fleets/{fleetId}/invitations/{invitationId}/accept|cancel` (`drivers.activate`). Accepting links the driver (`Driver.fleet`, `payoutTo: fleet`) and closes every other pending invitation of his; a driver already in a fleet is `409 conflict` (`already_in_fleet`), one on a trip `409 invalid_transition` (`on_trip`). An invitation lives `expiresDays` (7) days, then is `expired`; anything not `pending` is `409 invalid_transition`. The other side is told in the app (`GET /notifications`, kind `fleet_invitation`) and by one SMS (`smsText` / `smsTextRequest` in the receiver's language; a number without an account gets the app's install link). Rejecting or blocking a fleet cancels its pending invitations.
- **Fleet view.** `GET /driver/fleet` → `FleetView { fleet, drivers, vehicles }`: the owner sees the company with its code, every linked driver (`FleetDriver`) and every car; a member sees the company (no code, no e-mail), no drivers and every car of the fleet with `pickable` / `notPickableReason` and without the cars' documents (v0.18.0 §27, `carDocuments`; text fixed in v0.18.3). `GET /driver/fleet/earnings?from&to` (owner) → every driver's trips and earnings in the period and the total. The owner removes a driver with `POST /driver/fleet/drivers/{driverId}/remove`; a driver leaves with `POST /driver/fleet/leave`; an admin with `POST /admin/fleets/{fleetId}/drivers/{driverId}/remove`. None of these works during the driver's trip (`409 invalid_transition`, `on_trip`); the owner cannot leave (`fleet_owner`). Unlinking releases the car and takes the driver offline; he is back to waiting for a fleet and may join another with a new code.
- **Cars.** Fleet accounts add cars (`POST /driver/vehicles`, `Vehicle.fleetId` set; a member → `403`); an admin approves each (`POST /admin/vehicles/{vehicleId}/review`). `GET /driver/vehicles` gives a member every car of the fleet with `pickable` / `notPickableReason` (v0.18.0 §27; text fixed in v0.18.3) and the owner all of them with their documents, each with `driverId` (who has it picked) and `inUse` (that driver is online or on a trip). A driver picks his car with `PATCH /driver/profile { vehicleId }`: it must be approved and his fleet's, and (v0.14.0) every one of its `Vehicle.requiredDocuments` approved, else `409 documents_not_approved` (reason `vehicle_documents_not_approved`, `details` such as `vehicle:insurance`; the same when going online with it); a car in use by another driver is `409 conflict` (`vehicle_in_use`); a car picked by an offline driver moves (that driver picks again before going online). Going online needs `active`, a fleet (driver accounts) and an approved picked car (`no_vehicle`, `vehicle_not_approved`, `no_fleet`). A driver account without a fleet gets an empty list; the app says the fleet's vehicle details are awaited.
- **Documents.** `contract.json#driverOnboarding.documents.types` names every type with its owner (`driver` or `vehicle`), kind and names in en / sv / fr; `required[country]` lists them per country for the person (`driver`), the company (`fleet`) and each car (`vehicle`); `Driver.requiredDocuments`, `Driver.requiredFleetDocuments` and `Vehicle.requiredDocuments` carry the lists so the apps never compute them. Sweden: driver `terms`, `info_session`, `driving_license`, `profile_photo`, `taxi_driver_license`; company `company_registration`, `taxi_traffic_permit`, `tax_settings`, `bank_statement`; car `vehicle_registration`, `insurance`. France (as the ride platforms there ask): driver `terms`, `info_session`, `vtc_card`, `driving_license`, `national_id`, `profile_photo`; company `company_registration` (Kbis / SIRENE), `vtc_register_certificate`, `rc_pro_insurance`, `urssaf_certificate`, `national_id` (the manager's), `bank_statement` (RIB); car `vehicle_registration`, `insurance`, `vtc_sticker`. A fleet owner who drives needs his `driver` documents too. Kinds: `file` is uploaded with `POST /driver/documents` (multipart `type`, `ownerId` = `vehicleId` for a car, `expiresAt?`, `file`; at most 10 MB; jpeg, png, heic or pdf; `201`, status `in_review`; a new upload of the same type replaces the one in review or rejected) and decided with `POST /admin/documents/{documentId}/review` (`documents.approve`); `acceptance` is `terms`; `admin_check` is `info_session` (no file; an admin approves it after the session). Files are stored by the server, encrypted at rest in Europe, and read only through `GET /driver/documents/{documentId}/file` (the owner; the fleet owner for his drivers' and cars') and `GET /admin/documents/{documentId}/file` (`documents.approve`, written in the audit); `Document.fileUrl` is that path and never a public link.
- **Money.** `Driver.payoutTo`: `fleet` for a driver linked to a fleet (Movera pays the fleet's bank; the driver still sees his own trips and earnings), `self` for a fleet account. A driver without a fleet earns nothing yet (he cannot go online).
- **Admin.** `GET /admin/fleets?status&country&zoneId&q` (`drivers.read`), `GET /admin/fleets/{fleetId}` → `FleetView` with the code, `POST /admin/fleets/{fleetId}/review { expectedVersion, decision: approved | rejected | blocked, note? }` (`drivers.activate`; blocked takes every linked driver offline and withdraws their offers), `POST /admin/fleets/{fleetId}/code`, `POST /admin/fleets/{fleetId}/drivers/{driverId}/remove`, `GET /admin/drivers/{driverId}`. New drivers appear in the lists of the admins whose scope covers their city's zone (`zoneIds` is set on onboarding), and in every list before that for Super admins.

## 15. SOS and incidents (v0.7.0, safety part 1)
Owner safety part 1 decisions (2026-10-27); values in `contract.json#safety`.

The app keeps the Idempotency-Key and retries with it until it gets an answer; then it shows only "SOS sent" (no later update). Only the trip's own rider or driver, while the trip is live (`safety.sos.riderStatuses` / `driverStatuses`, the same list since v0.18.5: a driver is assigned, `accepted` … `approaching_dropoff`; owner G14 "SOS only during a trip" — a rider still searching gets only "Call 112"); otherwise `409 invalid_transition`, reason `trip_not_live`, with the trip. - **Admin reads.** `GET /admin/incidents` (`incidents.read`, zone-scoped, as before) and `GET /admin/incidents/{incidentId}` with `driverPosition`, the car's latest position, read live.
- **Alarm feed.** `GET /admin/incidents/stream` (SSE; without `Accept: text/event-stream` a JSON page, for polling): `incident_opened`, `incident_updated`, `incident_escalated`, `incident_closed`, each with the whole `Incident`, replay with `after` / `Last-Event-ID`. First only admins with `incidents.read` whose zones cover the incident's zone get its events; an `sos` or `driver_silent` incident not taken within `safety.escalateAfterSeconds` (120 s) is escalated (`escalatedAt`) and from then on goes to every signed-in admin. No SMS when nobody is online. The admin panel rings a repeating alarm for open `sos` and `driver_silent` incidents until one is taken.

### 3.8 Waiting at a middle stop (v0.7.1)

No free minutes. The driver app taps **Framme vid stoppet** (`POST /driver/trips/{tripId}/stops/{stopIndex}/arrive`) and, when the trip goes on, `…/leave`; both take `expectedVersion`, bump `version` and send `trip_projection`. The arrival is on **`stops[i].arrivedAt`** (and `stops[i].leftAt` after leaving) — the field the apps read, also after a reopen; the same taps are mirrored as `stopVisits: [{ stopIndex, arrivedAt, leftAt? }]` (kept for older readers; `contract.json#stopWaits.projection`). `stop_waiting` = Σ (leftAt − arrivedAt) / 60 × `stopWaitPerMin`, 100 % the driver's. Errors: `409 invalid_transition` with reason `stop_already_arrived`, `stop_out_of_order`, `stop_not_arrived` or `stop_already_left`; a trip not `in_trip` / `approaching_dropoff`: `409` (`not_on_trip`); a stop the trip does not have: `404` (`stop_not_found`).

## 18. Real data for the admin (v0.9.0, part 3)

Owner decisions of 2026-10-27: the live admin shows only what the server sends; a value without a source reads "Not connected yet" (sv "Inte kopplad än", fr "Pas encore connecté"), never a made-up number or a zero.

- **Payouts** (`contract.json#payouts`). A nightly job closes each driver's week (Monday 00:00 to Monday 00:00 in the zone's time, the driver's first zone) and makes one payout from the earnings entries of that week not yet in a payout. An admin can make one by hand for a driver and a date range (`POST /admin/payouts`): the same calculation, never counting an entry twice (409 `nothing_to_pay` when none is left). Lines (`fixtures/payouts.json`): trips = trip earnings + admin adjustments − waiting; waiting = the trips' `waiting` and `stop_waiting` fare lines; pickup pay, bonus, tips and fees (the driver's share of cancel and no-show fees) as credited; cash collected = − the cash the driver took. amount = the sum, possibly negative. Status `pending` until an admin marks it `paid` (`POST /admin/payouts/{payoutId}/paid`). `GET /admin/payouts` carries the lines; `GET /driver/payouts` only the totals.
- **Support** (`contract.json#support`). The rider and driver apps open tickets with `POST /support/tickets` (ride disputes and help requests; `category` from `support.categories`). Admin Support lists them (`GET /admin/tickets`, the admin's zones), opens one with its messages (`GET /admin/tickets/{ticketId}`) and answers (`POST /admin/tickets/{ticketId}/reply`; status `pending` by default, or `resolved` / `closed`). The apps read their tickets and the answers with `GET /support/tickets` and `GET /support/tickets/{ticketId}`.
- **Ratings** (`contract.json#ratings.tags`). Stars, optional tags and an optional comment, sent by both apps with `POST /trips/{tripId}/rating`. A rider uses `aboutDriver` tags, a driver `aboutRider` tags; any other tag is 400 `invalid_body`. Admin › Reviews lists them (`GET /admin/ratings`) and hides or restores one (`POST /admin/ratings/{tripId}/{from}/hide|restore`, with a reason, written in the audit). A hidden rating stops counting in the person's average (`Driver.rating`, `Rider.rating`) and in the low-rating risk signal; restoring counts it again.
- **Risk** (`contract.json#risk`). `GET /admin/risk/signals` counts three signals per person: cancels (percent, 30 days), failed payments (riders, 30 days) and low rating (drivers, the last 50 visible ratings). Fake GPS, many accounts on one phone and one card on many accounts come later.
- **KPIs** (`contract.json#kpis`). v0.10.3 money rules (`kpis.money`): `gross` = bookings (ride price + cancel/no-show fees, VAT included, tips not included); `fees` = the cancel/no-show fees inside it; `tips` apart; `refunds` counted on the trip's zone-local day (a later refund re-sums that day); `moveraEarnings` = commission + Movera's fee share − pickup pay − driver bonuses Movera paid (may be negative); net revenue (shown by the admin, not sent) = moveraEarnings − refunds; rows are per currency and never added across currencies; fleets see only driver earnings. `GET /admin/kpis?zoneId&fromDate&toDate` gives one `KpiDay` per zone and zone-local day: today counted live (`source: live`), earlier days from the nightly summary (`source: summary`). The summary job is safe to run again and has a backfill command.
- **Dispatch feed**. `GET /admin/dispatch/stream` (already in the contract): the offers sent, declined, expired, withdrawn and accepted, the lock and the driver bonuses, as SSE or a JSON page after a sequence number.

## 21. Zones from the server (v0.11.0)

Owner decisions of 2026-10-28 and #9 ("the server's list is the truth; the admin reads it and creates zones on the server"); the machine-readable rules are in `contract.json#zones`, cases in `fixtures/zones.json`.

- **Zone.** `{ zoneId, names { sv, fr, en }, country, currency, timeZone, kind: operating | airport, polygon [[lat, lng], …], bounds { south, west, north, east }, center, open, version, createdAt, updatedAt, updatedBy? }`. The polygon is the outline the admin draws on the map (3–500 points, not closed, not self-crossing); the server computes `bounds` (its rectangle, which earlier sections such as the driver surge map still use) and `center`.
- **Ids.** Fixed at creation. Stockholm keeps `Z001`–`Z009`; a new city zone is `<country>-<two letters>` (`FR-PC` Paris & Île-de-France, `TN-TC` Grand Tunis, as the apps already use); an airport is its IATA code (`ARN`, `BMA`, `CDG`, `ORY`).
- **Admin.** `GET /admin/zones?country` (`zones.read`, the admin's zones; Super admin all, open and closed). `POST /admin/zones` (201; `409 conflict zone_exists`), `PUT /admin/zones/{zoneId} { expectedVersion, names?, kind?, polygon? }`, `POST /admin/zones/{zoneId}/open|close { expectedVersion }` — all `zones.edit`, one admin is enough, one audit row each (`zone.create`, `zone.update`, `zone.open`, `zone.close`), `409 version_mismatch` on a stale version. An admin changes zones in its scope; creating needs the whole scope or a zone of the same country. `country`, `currency` and `timeZone` never change.
- **Never deleted.** There is no delete; a zone is closed. A closed zone takes no new rides; rides already booked go on.
- **Apps.** `GET /rider/zones?country`, `GET /driver/zones?country` → `{ zones }`: the open zones only, with polygon and names (shown in the app language). Read on start and on `config_published` with `doc: "zones"`, which every zone change sends on every rider and driver config stream (`doc: "content"` goes to the streams of its zone); the SSE id stays the app document's version.
- **Which zone.** Zones whose bounds hold the point, then whose polygon holds it (the edge counts as inside); an open zone before a closed one, a city zone before an airport, then the smallest. An airport inside a city zone (ARN, CDG, ORY) never takes the ride; it adds the airport fees, open or not.
- **Not here.** A quote or booking whose pickup is in no open zone is `403 forbidden`, reason `service_not_available`. The rider app shows "Movera isn't here yet" (sv "Movera finns inte här än", fr "Movera n’est pas encore ici") and cannot book.
- **Seed.** `Z001` Stockholm län (open); `FR-PC` Paris & Île-de-France (the whole region, Paris and 77, 78, 91, 92, 93, 94, 95; open) with the open airport zones `CDG` and `ORY` inside it (airport fees as at ARN), EUR, Europe/Paris; `TN-TC` Grand Tunis (Tunis, Ariana, Ben Arous, Manouba), TND, Africa/Tunis — closed until an admin opens it.

## 22. Ride check answers (v0.12.0, safety part 2)

Owner safety part 2 decisions (2026-10-28); values in `contract.json#safety.rideCheck`.

- **Who starts a check.** The apps, as today: the rider and driver apps watch the trip with the admin's `rider.rideCheck` / `driver.rideCheck` numbers and open the "Is everything OK?" card for a trigger `dropped_far`, `long_stop`, `off_route` or `possible_crash`. The app makes a `checkId` (unique per trip and side) and reports the check twice with `POST /rider/trips/{tripId}/ride-check` or `POST /driver/trips/{tripId}/ride-check`, body `RideCheckReport { checkId, trigger, at, answer?, position? }`: once when the card shows (no `answer`), once with the answer (`ok` | `need_help`). An answer without an earlier shown report is fine. The server starts no check itself.
- **Answers.** `ok` ("I'm OK"): only saved on the trip, no incident. `need_help` ("I need help"): opens the trip's `ride_check` incident at once (`raisedBy` the side, `alarm: true`): the admin panel rings the red alarm like an SOS and the incident escalates after `safety.escalateAfterSeconds` (120 s) untaken. The app does not call 112 for this answer by itself (its Call 112 button stays a separate SOS).
- **No answer.** When the server has a shown report and no answer `noAnswerSeconds` (120 s) after it received it, it opens the `ride_check` incident itself (`raisedBy: system`, `rideCheck.answer: no_answer`, `alarm: false`): it shows in the cases list without sound and never escalates.
- **One incident per trip.** At most one open `ride_check` incident per trip, for both sides. A no-answer incident that then gets `need_help` (either side) turns into `alarm: true` (`incident_updated`; the escalation clock starts then). Later checks join an open incident. An answer that comes after the no-answer incident opened is kept as `rideCheck.lateAnswer` (`incident_updated`); the admin still closes it.
- **When.** Only the trip's own rider or driver, while the trip is live (the SOS statuses) or up to `completedWithinMinutes` (30) after it completed (`dropped_far` comes at the end); otherwise `409 invalid_transition` with the trip.
- **Idempotent.** The app keeps the Idempotency-Key per report and retries until it gets an answer. The same `checkId` is the same check: a shown report for a known check changes nothing; `ok` then `need_help` moves to `need_help`; `need_help` then `ok` keeps `need_help`. The answer is `RideCheckReceipt { checkId, tripId, answer?, receivedAt, incidentId? }`; after answering the app shows only "Sent" (no later update).
- **Incident.** `kind: ride_check`, `severity: critical`, `alarm`, `rideCheck { checkId, trigger, by: rider | driver, answer: need_help | no_answer, shownAt?, answeredAt?, lateAnswer? }`, `position` (the phone's GPS from the report, when sent), with the usual trip, zone, rider, driver, car position and statuses (§15). `GET /admin/incidents?kind=ride_check` lists them; the stream carries them with the same zone rules. Every `Incident` now has `alarm` (`true` for `sos` and `driver_silent`): the panel rings for open incidents with `alarm: true` until taken.

## 23. Trip chat, masked calls and support scope (v0.13.0)

Owner decisions "chat only support roles in their zones" and of 2026-10-28; the machine-readable rules are in `contract.json#chat` and `contract.json#support`.

- **Who.** The trip chat (`GET|POST /trips/{tripId}/messages`) is between the trip's own rider and driver; anyone else is `404 not_found`. An admin reads and writes it only with `support.reply` (reading too) and only for a trip in one of the admin's zones; a Super admin sees all. Without the permission `403 forbidden`; outside the zones `403 forbidden`, reason `zone_out_of_scope`. There is no fleet owner ↔ driver chat.
- **Window.** Open while a driver is on the trip (`contract.json#tripStatus.driverAssigned`: `accepted` … `approaching_dropoff`) until drop-off. When the trip ends, the rider and the driver can no longer write (`409 invalid_transition`, reason `chat_closed`); the earlier hour after the trip is removed. The history stays readable while it is kept. Support may still write on an ended trip.
- **Retention.** A daily job deletes chat messages older than 90 days. Messages of a trip with a safety case (any incident on the trip: SOS, `driver_silent`, …) are kept with the case.
- **No phone numbers.** No rider or driver payload (trip views, `Message`, realtime envelopes, tickets in the apps) carries the other side's real phone number. The person's own profile keeps their own.
- **Calls.** `POST /trips/{tripId}/call` (the trip's rider or driver, while the chat is open) → `200 TripCall { tripId, proxyNumber, expiresAt }`: the app dials `proxyNumber` and the telephony provider bridges the call without showing either number. After drop-off `409 invalid_transition`, reason `chat_closed`. **The owner must pick a telephony provider** (number masking); its keys live in the server environment, never in git.

## 26. The final price before Collect cash (v0.18.1)

`contract.json#completePreview` (owner decisions of 2026-10-29, live bug A: "Server's final price (Recommended)").

- **Call.** `GET /driver/trips/{tripId}/complete-preview` → `CompletePreview { previewId, expiresAt, tripId, total: Money, cashDue: Money, driverEarnings: Money, earlyEnd: boolean, fareLines: FareLine[] }`. Only the trip's driver (anyone else `404 not_found`); only on board (`rider_onboard`, `in_trip`, `approaching_dropoff`), else `409 invalid_transition`, reason `trip_not_on_board`. No Idempotency-Key; the wallet is untouched.
- **Same as complete.** `total` and `fareLines` come from the same code as `POST /trips/{tripId}/complete` at that moment with the driver's latest fix (§3.5 "Driver ends the trip early"). `earlyEnd` is true beyond 300 m from the drop-off. `cashDue` = `total` less what the rider's wallet would pay; `driverEarnings` is the driver's part of `total` (the cash balance on the sheet).
- **Frozen for 2 minutes.** Each preview has a `previewId` and `expiresAt` (`freezeSeconds` 120) and replaces the trip's earlier one; the trip's version does not change. `POST /trips/{tripId}/complete { expectedVersion, previewId, cashCollected }` with the latest, unexpired `previewId` uses exactly the frozen price (`total`, `fareLines`, `driverEarnings`, `earlyEnd`): a driver who moves from 290 m to 310 m from the drop-off, or waits another minute, is not repriced. On a cash trip `cashCollected` must equal its `cashDue`.
- **Price changed.** `previewId` missing, unknown or expired: complete prices as now. When the app sent `previewId` and its `cashCollected` is not the cash part of that price (or of the frozen one), the answer is `409 conflict`, reason `price_changed`, with a fresh frozen preview in the error's `preview`; nothing is completed. The app shows the sheet again with the new amount and never resends the old one. A completed trip's cash collected is always the cash part of its final fare. Without `previewId` (older apps) the v0.5 rule stays: at most the fare less the wallet, else `400 invalid_request`, reason `cash_above_fare`.
- **Complete.** On a cash trip the app sends `previewId` and `cashCollected` = the `cashDue` it showed, then shows the `fare` of the returned `TripProjection`. Rider, receipt and history read the same trip fare. An older server without the preview (`404`) keeps the app on the old flow.
- **Earnings line.** The sheet's "Your earnings" ("Din intäkt", "Vos gains") is the preview's `driverEarnings`: the driver's own part of the price.
- **Apps.** "Collect <cashDue>"; when `earlyEnd`, also "Ending before the destination – price recalculated" (sv "Avslutas före destinationen – priset räknades om", fr "Fin avant la destination – prix recalculé"). A failed preview never shows the booked price as the amount to collect.

## 76. Admin masking of phone, e-mail and date of birth; Reveal with a reason; SOS reveal (v0.18.54)

Owner decisions of 2026-11-09 (START-HERE steps 35–37: Q40 "Yes, now", Q41 "Yes, logged"; inventory and the interpretation stated to the owner in Rules `plan/MASKING-INVENTORY-2026-11-09.md`). X-Api-Version stays `0.5`; no migration. `contract.json#adminMasking`.

- **Rule**: in every ADMIN answer, a rider's or driver's `phone`, `email` and `dateOfBirth`, and a fleet's `ownerEmail`, are MASKED unless the admin has the matching right — `riders.viewSensitive` for riders, `drivers.viewSensitive` for drivers and fleets (today: riders → support, safety, ops, super; drivers → dispatcher, compliance, fleet, ops, super; viewer and finance have neither and are masked from now on). - **Reveal routes (new)**: `POST /admin/riders/{riderId}/reveal { reason }` → `{ riderId, phone, email?, revealedAt }`; `POST /admin/drivers/{driverId}/reveal { reason }` → `{ driverId, phone?, email?, dateOfBirth?, revealedAt }` (`phone` when the driver record has one); `POST /admin/fleets/{fleetId}/reveal { reason }` → `{ fleetId, ownerEmail, revealedAt }`. Who: any admin with `riders.read` (riders) / `drivers.read` (drivers, fleets) and the person's zone in the admin's zones (else 403 `zone_out_of_scope`); `reason` 3–200 characters (else 400 `invalid_request`, reason `reason_required`); never cached by idempotency; audited `rider.reveal` / `driver.reveal` / `fleet.reveal` with `{ reason }` (never the values). The safety role (which has `riders.viewSensitive` but no `drivers.viewSensitive`) can thus call the driver in an SOS; one click on an open SOS reveals both numbers. `null` for a side the incident has no account for; a driver record without a phone answers `driver: { phone: null }`.
- **Export**: there is no CSV / export route today; a future export follows the same masking and the same rights.
- **Order / apps (Rule 0)**: contract → admin (accepts both full and masked values in every people view; shows Reveal with a reason dialog on `sensitiveMasked`; one click on an open SOS case reveals both numbers) → server (masks in the admin projections, adds the four routes and the `refunds.payouts_viewed` audit row). Rider and driver apps: no change needed (own profiles stay full).
